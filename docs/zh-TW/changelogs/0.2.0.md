## 新功能與變更

### 工具呼叫核准

以 `ApprovalRequiredAIFunction` 包裝的工具，要使用者核准後才會執行。`FunctionInvokingChatClient` 不會執行這種工具，
而是送出 `ToolApprovalRequestContent` 並結束串流。這個呼叫會顯示成等待使用者決定的卡片，上面有「核准」與「拒絕」鈕，
對話下方的進度列也會說明正在等待核准。不論 `ChatView.ShowsActivity` 怎麼設，這張卡片都會顯示。使用者決定完所有等待中的
呼叫後，`ChatRunner` 送出決定、該輪繼續：核准的呼叫會執行並完成，拒絕的呼叫顯示為已拒絕，模型也會知道。

- 沒按下按鈕就不會執行：沒有預設按鈕、沒有逾時，也沒有「全部核准」。
- 呼叫等待中時停止該輪（停止鈕、Esc 或 runner 的取消權杖）即視為拒絕。該輪以其他方式結束時也一樣拒絕，拒絕會記進歷史，
  之後的要求不會執行它。
- 使用者已核准、但該輪先結束而沒等到結果的呼叫，會在歷史中補上一筆「可能沒有執行」的結果，核准不會延續到下一次要求。
  載入保存的歷史時也一樣補上。
- 保存的歷史若以沒有回應的核准請求結尾，載入時該呼叫視為拒絕。
- 要求核准的呼叫若沿用對話中用過的 call id，到達時就拒絕，也不寫進歷史：`FunctionInvokingChatClient` 以 id 辨識呼叫，
  會把舊的結果當成它的結果，或讓之後每次要求都失敗。卡片會說明原因，但模型不會被告知，所以該輪就此結束。若某個 provider
  每次回應都用同樣的編號（`call_0`），第一次之後的每個核准請求都會這樣被拒絕。
- 該輪等待使用者的時間不計入它的時間，進度列與摘要都一樣。

### 附件

`ChatView.AllowsAttachments`（預設關閉）讓使用者用輸入框旁的附加鈕、或把檔案拖放到 view 上，替提問附加檔案。檔案先列在
輸入框上方（圖片有小預覽），隨提問一起送出；提問可以只有檔案、沒有文字。不允許的檔案不會附加，原因顯示在輸入框下方，
並由 `ChatView.AttachmentRejected` 回報。`ChatView.AddAttachmentAsync` 以同一套檢查附加應用程式自己來源的檔案或串流，
例如貼上的圖片。附件只在桌面驗證過；iOS 與 Android 尚未測試。

`ChatView.AttachmentLimits` 接受 `ChatAttachmentLimits`：

| 限制 | 預設值 |
|------|--------|
| `MaxFileSize` | 10 MB |
| `MaxCount` | 5 個檔案 |
| `MaxTotalSize` | 單次提問的檔案合計 20 MB |
| `AllowedMediaTypes` | PNG、JPEG、GIF、WebP、PDF |

- **類型採白名單，由內容判斷。** 圖片與 PDF 以開頭的位元組辨識，檔名表示的類型不符就拒絕，所以名為 `photo.png` 的程式
  不會被送出；副檔名是套件不認得的（例如 `photo.png.exe`）也一樣拒絕。純文字、Markdown、CSV、JSON 是已知類型但預設不允許，因為不少 provider 不收文字附件；加入它們的應用程式要在
  `ChatRunner.MessageSending` 轉換（它的 `Attachments` 可以修改）。文字必須是 UTF-8 且不含 NUL。
- **讀檔前先檢查大小。** 先檢查檔案回報的大小，讀取時超過上限一個位元組就停止，大檔案絕不會整個載入。
- **只把檔名送給模型**，不含路徑中的資料夾（那裡常有使用者名稱），也去掉不會畫出任何東西或會改變文字順序的字元。
  畫面上顯示檔名時，這些字元一律以跳脫形式呈現。
- **預覽絕不解碼大圖。** 先從圖片檔頭讀出尺寸；超過 4096 × 4096 像素、長邊超過短邊 20 倍、或不是 PNG、JPEG、GIF、WebP 的圖片不顯示預覽。
  載入的歷史中的圖片（從未經過限制檢查）也一樣。
- **只有空白的文字不算文字**：有附件時會略去，因為 provider 可能拒收。
- **內容不受信任。** 以 `DataContent` 原樣交給 provider；套件絕不把內容寫進提問文字，以免檔案假裝成使用者的要求。
- **provider 有自己的限制**，圖片通常較低（Anthropic 圖片上限 5 MB）：請把 `MaxFileSize` 設成所用 provider 的上限，
  否則較大的檔案會讓該輪失敗。
- **已知限制：** 圖片保留原有的中繼資料，包括位置；`SaveHistory` 會以 Base64 把檔案存進應用程式保存的歷史。

模型層的 `ChatConversation.AddUserPrompt(string, IReadOnlyList<DataContent>)` 與
`ChatRunner.SendAsync(string, IReadOnlyList<DataContent>, CancellationToken)` 接受附件，`UserPromptEntry.Attachments`
保存附件。以其他方式取得檔案的應用程式，可以用 `ChatAttachmentLimits.Check` 檢查內容。沒有 runner 時，
`PromptSubmittedEventArgs.Attachments` 把附件交給應用程式。

### 核准卡顯示什麼

使用者核准的就是工具會收到的內容，所以卡片以縮排 JSON 完整顯示參數。參數很長時在卡片內捲動，下方的提示說明還有內容。
不會畫出任何東西、或會改變周圍文字順序的字元（控制字元與格式字元，例如雙向覆寫字元與零寬字元）一律顯示為 `\u{202E}`
這類跳脫形式，套用在所有工具卡的參數、標題與結果。各種文字的字母照常顯示。

應用程式為 `ToolCallEntry` 註冊的樣板會取代這張卡片，這時完整顯示參數就是該樣板的責任。可以用
`ChatView.ApproveToolCallCommand` 與 `ChatView.RejectToolCallCommand` 決定呼叫。

### 在自己的迴圈裡核准

自己跑迴圈的應用程式照舊套用更新；`ToolApprovalRequestContent` 會把呼叫放進 `ChatTurn.PendingApprovals`。
`ChatTurn.WaitForApprovalsAsync` 等使用者決定完畢，回傳帶有決定的 user 訊息，應用程式在下一次要求時把它送給模型。使用者可能在串流還沒結束時就決定，所以串流結束後，只要
`ChatTurn.IsAwaitingApproval` 或 `ChatTurn.HasDecisionsToSend` 為 true，應用程式就要等待並取得決定。
`ChatTurn.Approve` 與 `ChatTurn.Reject` 可以從程式決定呼叫，例如自動核准使用者信任的工具。

### 重新生成與編輯上一則提問

最後一則回覆提供「重新生成」、上一則提問提供「編輯」，兩者都是游標停留時才出現的小按鈕。重新生成會把上一則提問（含附件）
再送一次，取代它以及之後的所有內容。編輯會把提問與附件放回輸入框，上方出現提示，並有按鈕（或 Esc）恢復輸入框原本的內容；
送出後取代上一則提問以及之後的所有內容。

- 有 `ChatRunner` 時，view 使用 `ChatRunner.RegenerateAsync` 與 `ChatRunner.EditLastPromptAsync`。兩者都會觸發
  `MessageSending`，並設定 `MessageSendingEventArgs.ReplacesLastPrompt`；處理常式取消時，對話維持原狀。文字是第一次送出時
  （經過當時的處理常式改寫後）的提問，所以會往文字加內容的處理常式要檢查 `ReplacesLastPrompt`，不要重複加。
- 沒有 runner 時，要應用程式把 `ChatView.AllowsRewind` 設為 `true` 才會出現按鈕：被取代的那幾輪中工具做過的事不會復原，
  只有應用程式知道這樣是否安全。之後 view 會觸發 `ChatView.RegenerateRequested`，編輯過的提問則以
  `PromptSubmittedEventArgs.IsEdit` 標示；應用程式在送出前呼叫 `ChatConversation.RewindLastPrompt`（它回傳被移除的提問）。
- 只用來回覆核准請求的 user 訊息不算提問；上一則提問之後應用程式自己的項目也會一併移除。應用程式自己加進項目的
  `UserPromptEntry` 也不算提問；`ChatConversation.LastPrompt` 指出會被取代的那一則，view 只對它提供編輯。

### 某個工具的呼叫專用的樣板

`ToolCallTemplate` 以應用程式自己的樣板顯示它指名的工具的每一次呼叫，取代預設的工具卡，例如天氣工具用天氣卡。
註冊方式與任何資料樣板相同，放在 view 上，或往上到 Application 的任何一層：

```xml
<chat:ChatView.DataTemplates>
  <chat:ToolCallTemplate ToolName="get_weather">
    <DataTemplate x:DataType="pc:ToolCallEntry">
      <local:WeatherCard />
    </DataTemplate>
  </chat:ToolCallTemplate>
</chat:ChatView.DataTemplates>
```

- 名稱以 Ordinal 比對，先比中的樣板勝出。
- 使用這種樣板的呼叫，即使 `ChatView.ShowsActivity` 關閉也會顯示：自己畫卡片的工具本來就是要給人看的。其他為
  `ToolCallEntry` 註冊的樣板照舊依 `ShowsActivity` 決定。
- 等待核准的呼叫也套用該工具的樣板。樣板可以用 `ChatView.ApproveToolCallCommand` 與 `ChatView.RejectToolCallCommand`
  決定呼叫，這時向使用者完整呈現工具會收到的內容，就是樣板的責任。

呼叫的參數與結果通常是 JSON 元素。`ToolCallEntry.TryGetArgument` 與 `ToolCallEntry.TryGetResult` 用
`JsonTypeInfo<T>` 把它們讀成指定型別（本身就是該型別的值，或從 JSON 讀），在裁剪與 AOT 的應用程式裡也能用。

### 放應用程式自己內容的位置

三組屬性，命名方式與 `EmptyContent`、`EmptyContentTemplate` 相同：

| 屬性 | 位置 | 例如 |
|------|------|------|
| `HeaderContent` | 對話上方；對話捲動時它固定不動 | 標題、模型選單、清除對話的按鈕 |
| `PromptHeaderContent` | 輸入框上方，在輸入區之內 | 提問的主題、快速指令 |
| `PromptFooterContent` | 輸入框下方，在輸入區之內 | 「回答可能有誤」的提醒 |

內容為 `null` 時不佔空間；對應的 `…Template` 用來顯示不是控制項的資料。既有樣板部件的名稱不變，所以應用程式自訂的
控制項樣板仍可使用；要顯示新內容，得自己加上對應的 presenter。

### `ChatTurn.AddEntry`

自己跑迴圈的應用程式可以在回合進行中加入自己的項目，例如請使用者選答案的卡片。它之前的回覆會結束，之後到達的文字會開新的回覆，
該輪的摘要排在它後面。與其他自訂項目一樣，它會顯示，但不會送給模型，保存的歷史也不含它。回合中直接加進
`ChatConversation.Entries` 的項目不會結束回覆：之後到達的文字仍會接在它上方的回覆裡。請改用 `ChatTurn.AddEntry`。

## 行為變更

### 載入的歷史中的檔案

載入的歷史中，帶有 `DataContent` 的 user 訊息會在提問項目中顯示檔案；有檔案但沒有文字的 user 訊息也會顯示成提問。
在 0.1，沒有文字的 user 訊息不會顯示。

### 工具呼叫的兩個新狀態

`ToolCallStatus` 新增兩個值，加在既有值之後，既有值的數字不變：

- `AwaitingApproval`：呼叫正在等待使用者。
- `Rejected`：呼叫沒有執行，因為有人說不：使用者或應用程式。有提供原因時，`ToolCallEntry.RejectionReason` 說明原因。
  應用程式自己拒收呼叫時（例如工具不接受的參數），改設這個狀態，不要用 `Failed`。

該輪結束時仍在等待核准的呼叫是 `Canceled`。

**處理方式**：列舉所有值的 `ToolCallStatus` `switch` 會讓兩個新值落到 default 分支；請替它們加上自己的分支。

## 已知限制

### 重新生成只帶回提問的文字與檔案

`ChatRunner.RegenerateAsync` 重送上一則提問時，只帶它的文字與 `DataContent` 附件。提問訊息中的其他內容（例如
`UriContent`），以及訊息的 `AuthorName` 與 `AdditionalProperties`，都不會再送出。以 `ChatConversation.AddUserPrompt`
加入的提問不會有其他內容，所以只影響應用程式自己組成、或從保存的歷史載入、user 訊息中含其他內容的情況。

**處理方式**：提問含其他內容的應用程式自己處理重新生成：呼叫 `ChatConversation.RewindLastPrompt`（它回傳被移除的完整訊息），
在自己的迴圈裡送出這則訊息；不設 runner，改設 `ChatView.AllowsRewind` 並處理 `ChatView.RegenerateRequested`。

### view 送出時，處理常式丟出的例外不會被觀察到

view 透過 runner 送出（提問、重新生成、編輯）時不會等待結果。`ChatRunner.MessageSending` 或 `ChatRunner.ResponseReceived`
的處理常式丟出例外時，該次送出就此結束，例外也不會回報到任何地方，只會成為未被觀察的工作例外。

**處理方式**：在這些處理常式裡自行攔截並回報例外。

### 取消編輯的同時改動對話，會遺失草稿

使用者編輯上一則提問、而 `MessageSending` 處理常式取消了修改後的提問時，view 會把提問放回輸入框並維持編輯狀態，之後按 Esc
仍可還原輸入框原本的內容。若同一個處理常式同時改動了對話（清空、或加入提問），正在編輯的提問就不再是最後一則，編輯隨即結束，
原本的草稿不會還原。

**處理方式**：改動對話的處理常式不要同時取消送出，或在送出之後再改動，例如放在 `ResponseReceived`。
