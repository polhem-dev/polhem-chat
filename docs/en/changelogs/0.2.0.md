# Polhem.Chat 0.2.0 — Release Notes

[繁體中文](../../zh-TW/changelogs/0.2.0.md)

This file holds the details behind the `[0.2.0]` entry in [CHANGELOG.md](../../../CHANGELOG.md). The version is not
released yet; the entry is `[Unreleased]` until it is.

What each kind of application has to act on:

- **Applications that switch over `ToolCallStatus`**: [Two new tool call states](#two-new-tool-call-states).
- **Applications that run tools that change things**: wrap them in `ApprovalRequiredAIFunction` ([Tool call
  approval](#tool-call-approval)).
- **Applications that run their own loop**: [Approval in a loop of your own](#approval-in-a-loop-of-your-own).

## New features and changes

### Tool call approval

A tool wrapped in `ApprovalRequiredAIFunction` runs only after the user approves it. `FunctionInvokingChatClient`
does not run such a tool: it sends a `ToolApprovalRequestContent` instead and ends the stream. The call then shows as a
card that waits for the user, with an Approve and a Reject button, and the line under the conversation says it waits for
approval. The card shows however `ChatView.ShowsActivity` is set. Once the user has decided on every waiting call,
`ChatRunner` sends the decisions and the turn goes on: an approved call runs and completes, a rejected one shows as
rejected, and the model hears about it.

- Nothing runs without the button: there is no default button, no time-out and no "approve all".
- Stopping the turn while a call waits, with the stop button, Esc or the runner's token, rejects the call. A turn that
  ends any other way rejects it too, and the rejection goes into the history, so a later request cannot run it.
- A call the user approved whose result never arrived, because the turn ended first, is closed in the history with a
  result that says it may not have run, so the approval does not carry over to the next request. A saved history is
  closed the same way when it loads.
- A saved history that ends with a request nobody answered loads with the call rejected.
- A request for a call id the conversation used before is rejected as it arrives and left out of the history:
  `FunctionInvokingChatClient` keys calls by id, and would either take the old result for it or fail every later
  request. The card says why; the model is not told, so the turn ends there. A provider that numbers its calls the same
  way in every response (`call_0`) would have every request after the first rejected this way.
- The time the turn waits for the user is left out of its time, in the progress line and in the summary.

### What the approval card shows

The user approves what the tool receives, so the card shows the arguments as indented JSON, in full. Long arguments
scroll inside the card, and a note under them says there is more to read. Characters that draw nothing or reorder the
text around them (control and format characters, such as the bidirectional overrides and zero-width characters) show
as escapes like `\u{202E}`, in the arguments, the title and the result of every tool call card. Letters of any script
show as they are.

A template the application registers for `ToolCallEntry` replaces the card, and then showing the arguments in full is
the template's task. `ChatView.ApproveToolCallCommand` and `ChatView.RejectToolCallCommand` decide a call from it.

### Approval in a loop of your own

An application that runs its own loop applies the updates as before; a `ToolApprovalRequestContent` puts the call in
`ChatTurn.PendingApprovals`. `ChatTurn.WaitForApprovalsAsync` waits until the user has decided and returns the user
message with the decisions, which the application sends to the model with its next request. The user may decide while
the stream is still open, so once a stream ends the application waits when `ChatTurn.IsAwaitingApproval` or
`ChatTurn.HasDecisionsToSend` is true. `ChatTurn.Approve` and `ChatTurn.Reject` decide a call from code, for example to
approve a tool the user trusts.

### A template for the calls of one tool

`ToolCallTemplate` shows each call of the tool it names with a template of the application's own, for example a weather
card for a weather tool, in place of the default tool call card. Register it like any data template, on the view or on
any ancestor up to the application:

```xml
<chat:ChatView.DataTemplates>
  <chat:ToolCallTemplate ToolName="get_weather">
    <DataTemplate x:DataType="pc:ToolCallEntry">
      <local:WeatherCard />
    </DataTemplate>
  </chat:ToolCallTemplate>
</chat:ChatView.DataTemplates>
```

- The name is compared ordinally, and the first template that matches wins.
- A call shown with such a template shows even while `ChatView.ShowsActivity` is off: a tool that draws its own card is
  there to be seen. Other templates for `ToolCallEntry` follow `ShowsActivity` as before.
- A call that waits for approval shows with the tool's template too. The template can decide it with
  `ChatView.ApproveToolCallCommand` and `ChatView.RejectToolCallCommand`, and then showing the user everything the tool
  will receive is its task.

The arguments and the result of a call are usually JSON elements. `ToolCallEntry.TryGetArgument` and
`ToolCallEntry.TryGetResult` read them as a type, from a value of that type or from JSON, with a `JsonTypeInfo<T>`, so
they work in trimmed and AOT applications.

### Places for the application's own content

Three pairs of properties, named like `EmptyContent` and `EmptyContentTemplate`:

| Property | Where | For example |
|----------|-------|-------------|
| `HeaderContent` | Above the conversation; it stays in place while the conversation scrolls | A title, a model picker, a button that clears the conversation |
| `PromptHeaderContent` | Above the prompt box, inside its area | What the prompt is about, quick commands |
| `PromptFooterContent` | Below the prompt box, inside its area | A note that answers can be wrong |

Each takes no room while it is `null`, and its `…Template` shows data that is not a control. The names of the existing
template parts do not change, so a control template of the application's own keeps working; it shows the new content
only if it adds presenters for it.

### `ChatTurn.AddEntry`

An application that runs its own loop can add an entry of its own while a turn is in progress, for example a card that
asks the user to pick an answer. The reply before it ends, so text that arrives later starts a new reply, and the turn's
summary comes after it. Like any entry of the application's own, it is shown but not sent to the model, and the saved
history does not keep it. An entry added straight to `ChatConversation.Entries` during a turn does not end the reply: text
that arrives after it is still appended to the reply above it. Add it with `ChatTurn.AddEntry` instead.

## Changes in behaviour

### Two new tool call states

`ToolCallStatus` has two new values, added after the existing ones so their numbers do not change:

- `AwaitingApproval`: the call waits for the user.
- `Rejected`: the call did not run because someone said no, the user or the application. `ToolCallEntry.RejectionReason`
  says why when a reason was given. An application that refuses a call itself, for example arguments its tool does not
  accept, sets this state instead of `Failed`.

A call that waited for approval when its turn ended is `Canceled`.

**What to do**: a `switch` over `ToolCallStatus` that names every value gets the two new ones through its default
branch; give them a branch of their own.
